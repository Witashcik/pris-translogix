## 3. Описание разработанного сервиса

**TransLogix** — это прототип интеллектуальной логистической системы, предназначенной для оптимизации маршрутов доставки и контроля складских запасов.

Сервис ориентирован на компании, которые занимаются доставкой товаров из складов в розничные точки. Основная идея системы — помочь диспетчеру быстрее принять решение: от какого склада выполнять доставку, в каком порядке посещать точки и каких товаров может не хватить в ближайшие дни.

Прототип реализован как веб-приложение:

- **Frontend:** HTML, CSS, JavaScript без отдельного сборщика;
- **Backend:** FastAPI;
- **Хранение данных:** in-memory структуры данных Python;
- **Документация API:** Swagger UI;
- **Тестирование:** pytest и TestClient;
- **Развёртывание:** локальный запуск и Docker Compose.

Для первой лабораторной работы было решено не использовать полноценную базу данных и настоящую ML-модель, чтобы сохранить простоту запуска. Вместо этого реализована упрощённая AI-like логика: эвристики маршрутизации и сценарный прогноз спроса.

## 4. Основные функции сервиса

### 4.1. Dashboard

На главной странице отображаются ключевые показатели системы:

- количество складов;
- количество точек доставки;
- количество срочных доставок;
- средняя загрузка складов.

Этот блок нужен для быстрой оценки состояния логистической системы.

### 4.2. Оптимизация маршрута

Пользователь может выбрать склад и стратегию маршрутизации:

- **Приоритет + расстояние** — сначала выбираются точки с высоким приоритетом, затем ближайшая из них;
- **Ближайшая точка** — маршрут строится по минимальному расстоянию;
- **Только срочные** — в маршрут попадают только доставки с высоким приоритетом.

После расчёта интерфейс показывает:

- общую дистанцию маршрута;
- примерное время выполнения;
- условную стоимость топлива;
- оценку качества маршрута;
- визуальную последовательность точек доставки.

### 4.3. Прогноз складских запасов

Пользователь выбирает склад, период прогноза и сценарий спроса:

- обычный спрос;
- промо / высокий спрос;
- сниженный спрос.

Сервис рассчитывает прогнозируемый спрос, остаток после выбранного периода и статус товара:

- `ok` — запаса достаточно;
- `warning` — запас близок к минимальному;
- `risk` — товара не хватит, нужно пополнение.

### 4.4. Оповещения и история операций

Сервис показывает потенциальные риски по складам и товарам. Также сохраняется история последних действий пользователя: построение маршрута и расчёт прогноза.

### 4.5. Метрики производительности

В прототип добавлен endpoint метрик, который показывает:

- статус сервиса;
- количество складов;
- количество точек доставки;
- количество записей истории;
- использование оперативной памяти;
- текущую нагрузку CPU.

## 5. Этапы разработки

### 5.1. Проработка архитектуры

На первом этапе с помощью большой языковой модели были определены основные пользовательские сценарии:

1. Диспетчер открывает систему и видит общую сводку.
2. Диспетчер выбирает склад и строит маршрут доставки.
3. Сотрудник склада проверяет прогноз запасов.
4. Руководитель смотрит оповещения и технические метрики.

Также была определена первичная структура данных:

- склад;
- точка доставки;
- заказ / спрос по товарам;
- маршрут;
- прогноз запасов;
- история операций;
- метрики сервиса.

### 5.2. Генерация и доработка кода

Код был подготовлен итерационно: сначала был создан минимальный backend и простой frontend, затем интерфейс был расширен до dashboard-формата. Были добавлены выпадающие списки, сценарии спроса, визуальная лента маршрута, таблица прогноза запасов, история операций и Docker Compose.

### 5.3. Тестирование

Тестирование проводилось двумя способами:

1. **Ручное тестирование через frontend:** проверялись кнопки, выпадающие списки, отображение маршрута, прогноз запасов, оповещения и метрики.
2. **Автотесты API:** проверялись основные backend endpoint'ы.

Проверяемые endpoint'ы:

- `GET /health`;
- `GET /api/dashboard`;
- `POST /api/optimize-route`;
- `POST /api/inventory/forecast`;
- `GET /api/alerts`;
- обработка ошибки при несуществующем складе.

## 6. Анализ полученного результата

### 6.1. Степень успеха разработки

В результате работы был получен рабочий MVP-прототип. Основные сценарии работают: пользователь может открыть интерфейс, построить маршрут, рассчитать прогноз запасов, посмотреть риски и метрики.

Для учебной лабораторной работы степень успеха можно оценить как высокую, так как реализована не только серверная часть, но и наглядный frontend для демонстрации.

### 6.2. Выявленные проблемы

Критических видимых багов в финальной версии не выявлено. Однако у прототипа есть ограничения:

- данные хранятся в памяти и сбрасываются после перезапуска;
- нет авторизации пользователей;
- нет подключения к реальным картам;
- нет настоящей ML-модели прогнозирования;
- маршрутизация использует эвристику, а не полноценный алгоритм оптимизации.

Эти ограничения допустимы для proof-of-concept, но должны быть устранены перед production-использованием.

### 6.3. Качество кода

Код разделён на backend, frontend, тесты и документацию. Backend содержит модели данных, API endpoint'ы и бизнес-логику. Frontend вынесен в отдельные файлы `index.html`, `style.css`, `app.js`.

Плюсы:

- понятная структура проекта;
- наличие Swagger-документации;
- наличие автотестов;
- простая установка и запуск;
- есть Dockerfile и docker-compose.yml.

Минусы:

- часть данных захардкожена;
- нет отдельного слоя repository/service;
- нет базы данных;
- нет полноценной обработки всех возможных ошибок.

### 6.4. Производительность

Прототип работает быстро, так как не использует тяжёлые ML-модели и внешние API. Расчёт маршрута выполняется за миллисекунды, потому что объём демо-данных небольшой.

Использование оперативной памяти и CPU можно проверить через frontend-блок «Метрики прототипа» или endpoint `GET /api/metrics`.

Основное ограничение производительности появится при росте количества точек доставки. В таком случае потребуется оптимизировать алгоритм маршрутизации и вынести данные в базу данных.

### 6.5. Возможности развёртывания

Сервис можно запускать локально через `uvicorn` или через Docker Compose:

```bash
docker compose up --build
```

Так как сервис не требует тяжёлой LLM и базы данных, его можно развернуть на большинстве недорогих серверов или учебных хостингов. Для полноценной версии можно добавить PostgreSQL, Redis, авторизацию и отдельный frontend-фреймворк.

## 7. Рефлективное заключение

В результате лабораторной работы был создан рабочий прототип сервиса TransLogix. Подход вейб-кодинга оказался полезен для быстрого получения MVP: сначала была сформирована идея и структура системы, затем на их основе был создан код, после чего проект был доработан вручную.

Главный плюс подхода — высокая скорость разработки. Главный минус — необходимость внимательно проверять сгенерированный код, так как модель может использовать хардкод, упрощать бизнес-логику или пропускать обработку ошибок.

Полученный сервис можно оценить как MVP уровня 7/10: он наглядно демонстрирует основные функции TransLogix, имеет frontend, backend, API-документацию, тесты и Docker Compose. Для production-версии потребуются база данных, авторизация, интеграция с картами и настоящая модель прогнозирования спроса.
